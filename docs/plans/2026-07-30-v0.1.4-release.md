# v0.1.4 Release Implementation Plan

> **For Agent:** REQUIRED SUB-SKILL: Follow this plan task-by-task.

**Goal:** Publish Little Alphaxiv v0.1.4 with accurate bilingual product documentation, a complete changelog, verified code, and a GitHub Release.

**Architecture:** Treat the Git history from v0.1.3 through the release commit as the source of truth. Maintain separate current-product, historical-changelog, and release-summary documents, then publish only from a CI-green merge commit on `main`.

**Tech Stack:** Markdown, npm/Vitest/TypeScript, Python 3.10/pytest, Git, GitHub CLI

---

### Task 1: Build the release evidence map

**Files:**
- Review: `CHANGELOG.md`
- Review: merged PRs and `git log v0.1.3..HEAD`

1. Map every merged PR after v0.1.3 to Added, Changed, or Fixed.
2. Group related follow-up PRs under one user-facing outcome.
3. Record migrations, compatibility defaults, and known limitations.

### Task 2: Write release documentation

**Files:**
- Create: `docs/releases/v0.1.4.md`
- Modify: `CHANGELOG.md`
- Modify: `README.md`
- Modify: `README.zh-CN.md`

1. Write release highlights and upgrade guidance.
2. Add the complete v0.1.4 changelog and correct comparison links.
3. Update both README feature lists and roadmap status.
4. Check that English and Chinese documentation describe the same features.

### Task 3: Synchronize version metadata

**Files:**
- Modify: `frontend/package.json`
- Modify: `frontend/package-lock.json`

1. Change the package version from `0.1.0` to `0.1.4` in both manifests.
2. Search the repository for stale release-version references.

### Task 4: Verify the release candidate

**Files:**
- Test: frontend and backend suites

1. Run `npm run typecheck` from `frontend/`.
2. Run `npm test` from `frontend/`.
3. Run `npm run build` from `frontend/`.
4. Activate `Agent_env` and run `python -m pytest` from `backend/`.
5. Review the final diff and all Markdown links.

### Task 5: Merge through the protected workflow

1. Commit the release candidate.
2. Push `codex/release-v0.1.4` to `origin`.
3. Open a pull request describing documentation and verification evidence.
4. Wait for all required CI checks to pass.
5. Merge the pull request and update local `main`.

### Task 6: Publish and verify v0.1.4

1. Tag the merged `main` commit as `v0.1.4` and push the tag.
2. Create a non-prerelease GitHub Release using `docs/releases/v0.1.4.md`.
3. Attach a Linux portable artifact only if it was built and smoke-tested.
4. Verify the public tag, release body, release classification, and assets.
5. Remove the worktree safely after publication.
